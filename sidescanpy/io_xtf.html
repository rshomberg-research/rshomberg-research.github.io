XTF#

.xtf (eXtended Triton Format) is the most common vendor-neutral sidescan format: Klein, EdgeTech and others can record or export it. The reader follows the specification’s revision 42 (Exail) and has been checked against EdgeTech 4200 files recorded by Isis, and against public files written by EdgeTech Discover 7.22, Isis 7.0.41 (Benthos SIS-1624) and KleinXlt 4.0 (small cuts of them are the fixtures in tests/data/public/). Only sonar packets are read; other packet types are counted and skipped.

from sidescanpy.io import read_and_convert, read_and_convert_segments
from sidescanpy.io.xtf import convert, read_xtf, split_by_sample_rate

# One survey per run of constant range (see "Range changes" below):
for stem, survey in read_and_convert_segments(path):
    ...
# or, step by step:
surveys = [convert(seg) for seg in split_by_sample_rate(read_xtf(path))]

survey = read_and_convert([path], "xtf")      # whole file, one survey

read_xtf_header, iter_packets, count_packets and read_xtf_pings give the file header, the raw packets and the recorded pings (samples in their recorded dtype) for inspection. write_subset(src, dst, n_pings=, start_ping=) copies the header and a run of pings to a new file, byte for byte (for making small test files).

File structure#

A 1024-byte file header (system, recording program, sonar name, navigation units, and one 128-byte ChanInfo per channel; more than six channels spill into further 1024-byte blocks), then packets. Every packet starts with the magic 0xFACE, a header type and its total byte count, which the reader uses to step from packet to packet. A sonar packet is a 256-byte ping header followed, per channel, by a 64-byte channel header and that channel’s samples.

Mapping to the standard model#

Survey

XTF source

frequency key hz_<Hz>

ChanInfo.Frequency (kHz) of a port/starboard pair

backscatter_intensity (ping, channel, sample)

port (TypeOfChannel 1) and starboard (2) samples, float32; sample 0 nearest the sonar on both sides (XTF stores port far -> near, so port is reversed)

valid_samples

per-ping NumSamples; padding beyond it is NaN

latitude, longitude

SensorYcoordinate, SensorXcoordinate (degrees, NavUnits 3)

heading_deg, pitch_deg, roll_deg, heave_m

SensorHeading, SensorPitch (nose up +), SensorRoll (port up +), Heave

depth_m

SensorDepth

altitude_m, fathometer_reading_m

SensorPrimaryAltitude; 0 is NaN

sound_vel_ms

SoundVelocity, doubled when below 1000 m/s (see below)

sample_rate_hz

NumSamples / TimeDuration

time

Year … Second + HSeconds (10 ms resolution)

navigation / attitude records

every ping header (source = extracted_from_xtf_ping_headers)

pulse_length_us is not in the XTF headers and is 0.0. Gain codes are not interpreted. Dataset attributes prefixed xtf_ record the recording program, sonar, channel numbers and names, and counts of reader anomalies.

Conventions and caveats#

  • Sound velocity may be halved. Some recorders store c / 2 in SoundVelocity (750 for 1500 m/s). Values below 1000 m/s are doubled, and the result is cross-checked against 2 * SlantRange / TimeDuration; a disagreement over 5 % is logged at WARNING.

  • Range changes. The model has one sample_rate_hz per frequency, but some recorders change the range setting mid-file while keeping the sample count, so the sample interval changes. split_by_sample_rate cuts a file’s pings into consecutive runs within which every port/starboard channel keeps its rate (NumSamples / TimeDuration, relative tolerance rtol, default 1 %, measured against the run’s first ping); pings where a channel is absent never cause a cut. Runs shorter than min_pings (default 50) are dropped, since a change often leaves a few pings at an intermediate setting. Each run is a view of the file’s arrays and converts to its own survey, with attributes xtf_segment_index, xtf_segment_count, xtf_segment_ping_start, xtf_segment_ping_stop, xtf_file_pings, xtf_runs_dropped_short and xtf_pings_dropped_short_runs. read_and_convert_segments and sidescan-convert survey do this for every XTF file and name the outputs <stem> (one run) or <stem>_seg01, <stem>_seg02, … (several). Converting an unsplit file with mixed rates still works: the most common rate is used, the other pings are counted in xtf_pings_other_sample_rate and a WARNING is logged, since their ranges are scaled wrongly by the ratio of the rates.

  • Pings with fewer channels than declared. Some EdgeTech files begin with pings that hold only the low-frequency pair while declaring all four channels. The reader walks channel blocks by the packet byte count; those pings are left out of the high frequency (which keeps its own ping axis) and counted in xtf_pings_absent.

  • Projected coordinates (NavUnits 0) are not supported and raise NotImplementedError.

  • Sample scaling. Samples are scaled by 2**-Weight from the channel header. Some older files carry meaningless Weight values (for example -8408), which make every sample unusable. If a converted file’s samples are all infinite, NaN or zero, check xtf_weight_min and xtf_weight_max in the dataset attributes.

  • Older KleinXlt files. Some KleinXlt 3.0 files leave the channel SampleFormat at 255, which the reader rejects with ValueError.

  • Recorder gain. Gain codes are read but not interpreted, and nothing in the file says whether the recorder applied TVG. Measure it with analysis.fit_range_decay before correcting (Limitations).
