sidescanpy.io.xtf.reader#

Low-level XTF (eXtended Triton Format) reader.

Reads the file header, frames packets, and parses sonar packets into per-ping header records and per-channel sample arrays. The converter to the standard survey model is sidescanpy.io.xtf.converter; read_xtf is the per-file entry point that feeds it.

File layout#

A file starts with a 1024-byte header holding up to six ChanInfo channel descriptions; with more than six channels the remaining ChanInfo entries follow contiguously in further 1024-byte blocks. Packets follow. Each starts with the magic 0xFACE, a header type and NumBytesThisRecord, the packet’s total size including any padding. That byte count is authoritative: the reader steps from packet to packet with it, never with sizes derived from the packet contents. A packet with a bad magic triggers a forward scan for the next 0xFACE (counted, and logged at WARNING); a truncated final packet is logged at WARNING and ends the read.

A sonar packet (header type 0) is a 256-byte ping header followed, for each channel, by a 64-byte channel header and NumSamples samples. The sample type comes from the file header’s ChanInfo entry for that channel (SampleFormat, else BytesPerSample; a SampleFormat the specification does not define, such as 255, counts as unset).

Channel blocks are walked using the packet byte count#

NumChansToFollow in the ping header is treated as an upper bound. Channel blocks are parsed while at least a full 64-byte channel header remains inside the packet; a channel whose samples would run past the packet end is clipped to the samples that fit. Each mismatch kind is logged at WARNING once per file with a count.

Evidence for this rule (EdgeTech 4200 files recorded by Isis, four channels declared in the file header: port/starboard at 120 kHz as channels 0/1 and at 410 kHz as channels 2/3, BytesPerSample 2):

  • In two such files the first sonar packets (2976 of 25539 in one file, 1680 of 20475 in the other, a single contiguous run at the start) are 4480 bytes long while their ping headers say NumChansToFollow = 4 and the first two channel headers say NumSamples = 1024. Normal packets are 8704 = 256 + 4 * (64 + 1024 * 2) bytes.

  • 4480 = 256 + 2 * (64 + 1024 * 2) exactly: the packet holds two complete channel blocks (channel numbers 0 and 1, the low-frequency pair) and nothing else. The “third channel header” a reader trusting NumChansToFollow would parse starts with 0xFACE: it is the next packet.

  • The samples are 16-bit, 1024 per channel as declared. Read as uint16, adjacent samples correlate (lag-1 r = 0.96 and 0.79 over the two runs, 0.86 and 0.80 in the same files’ normal pings), values stay within the normal pings’ 0..32767 range, and medians are comparable (1148 vs 1505, 285 vs 731). Read as 8-bit, adjacent samples do not correlate (r = -0.01 and -0.46). The first pings of each run are faint (high byte zero in 88-99.99 % of the first 200 pings), rising to the normal level. Ping numbers are continuous across the switch to four-channel packets, navigation is continuous, and the low-only pings repeat faster (0.08 s vs 0.14 s at 100 m range, 0.21 s vs 0.42 s at 300 m).

So those pings carry only the low-frequency pair; the high-frequency channels are absent, not empty. pyxtf 1.5.0 trusts NumChansToFollow and fails on such packets.

Sample arrays#

Samples keep their recorded dtype (uint8/uint16/uint32/float32), so values are bit-identical to the file. A channel’s array is (n_ping, max_samples) over all sonar pings of the file; pings where the channel is absent or shorter are zero-padded on the right, and the true length is in num_samples (0 where absent, with present False). The converter decides whether padding becomes NaN.

sidescanpy.io.xtf.reader.iter_packets(path, header_types=None, stats=None)#

Stream the packets of an XTF file.

Parameters:
pathstr or Path

XTF file.

header_typesiterable of int, optional

Header types to yield. Others are skipped by their byte count without reading their body. Default: yield every packet.

statsPacketStats, optional

Filled in place with counts as packets are framed (useful because a generator has no return value to the caller).

Yields:
XtfPacket

Packets in file order.

Notes

Packets whose header type is not defined by the specification are counted in stats.unknown and logged at DEBUG; they are yielded like any other when no filter is given. A bad magic number or a byte count smaller than the packet start triggers a forward scan for the next 0xFACE (logged at WARNING). A packet extending past the end of the file is logged at WARNING and ends iteration.
